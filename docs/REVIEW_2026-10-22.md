# 추가 개발·성능·리팩터링 검토

2026-10-22 검토 당시의 발견 기록이다. 후속 구현으로 아래 P1 상태 무효화, P2 SSH 중복 요청, P2 상태 집계와 관련 리팩터링을 반영했다. 수정 및 검증 기록은 [DEVELOPMENT.md](DEVELOPMENT.md), 비교 측정과 쓰기 비용은 [PERFORMANCE.md](PERFORMANCE.md)를 따른다. 아래 재현 수치는 수정 전 결과이며, 운영·공개 배포의 후속 제안 전체가 구현된 것은 아니다.

## 발견 사항

### P1: 원본 변경을 발견한 재개의 상태 무효화

transfer._execute의 전송 전 _planned_source 검사가 공통 실패 처리 try 밖에 있다. VERIFIED 작업의 원본 파일을 다른 크기로 수정한 뒤 resume하면 VerificationError로 전송을 거부하지만 DB의 계획 VERIFIED와 verified_files=1이 그대로 남는 현상을 실제 rsync 시험으로 재현했다. 이미 발견한 변경이 status에 반영되지 않는다. 전송을 계속하거나 원본을 훼손하는 문제는 아니다.

사전 세대 검사와 공통 실패 처리를 연결하고 크기/mtime/하위 디렉터리 변경 시 검증 증거 무효화, 대상 미변경, 새 계획 요구를 검사해야 한다. 권한 부족이나 구성 오류까지 무조건 같은 실패로 처리하지 않도록 오류 의미를 구분한다.

### P2: SSH 파일별 왕복 호출 비용

WSL Python 3.14.4, Linux /tmp에서 7바이트 파일 10개를 실제 loopback SSH로 push했다. Session.call 진입을 계수하면 계획 34회, run의 전송·전체 검증까지 678회였다.

| run RPC | 호출 수 |
|---|---:|
| check | 150 |
| hash | 30 |
| hello | 1 |
| identity | 9 |
| idle | 1 |
| mount | 307 |
| stat | 170 |
| utime | 10 |

이는 rsync 패킷 수나 SSH 연결 수가 아니라 helper RPC 호출 수다. 작은 파일에서는 왕복 지연의 영향이 클 수 있다. check/mount/stat을 한 요청 안에서 수행하거나 제한된 배치로 처리하는 방향을 제안한다. 경로·마운트·세대·전체 해시 검사를 유지해야 하며 장기 캐시로 안전 검사를 우회하지 않는다. 실제 WAN 처리량은 측정하지 않았다.

### P2: 상태 감시의 반복 전체 집계

state.summary는 entries/file_results 집계와 증분 기준의 삭제 후보 count/sample을 매번 조회한다. 삭제 후보가 없으면 sample의 LIMIT 20도 baseline 전체 대조를 피하지 못한다. monitor.watch는 기본 2초 간격으로 summary를 호출한다.

Linux /tmp의 SQLite에 각 20만 행인 baseline/current 계획을 만들고 모든 경로를 일치시켰다. 파일당 size=1, action=COPY, file_results는 비어 있다. summary(current)를 네 번 호출한 중앙값은 lineage 연결 전 20.9ms, scan_complete=1인 lineage 연결 후 137.3ms로 약 6.6배였다. 삽입 시간은 제외했다. 실제 파일 상태 집계 비용과 백만 규모 성능은 별도 검증이 필요하다.

완료 계획의 고정 집계·삭제 후보 통계와 커밋 단위 진행 집계를 저장해 감시 조회를 줄일 수 있다. 추가 카운터의 쓰기 비용 및 중단/재개 시 DB와의 일관성을 함께 검증해야 한다.

## 리팩터링 범위

- _execute의 사전 검사·상태 전이·실패 처리를 명확하게 분리하는 작업을 위 상태 문제 수정과 함께 진행한다.
- 계획 재개/증분/전송 재개에서 반복되는 설정 호환성 비교를 같은 계약으로 묶는 작업을 검토한다. 재시도/시간 제한만 변경 가능한 기존 계약을 유지한다.
- 독립 실행되는 SSH helper를 일반 모듈처럼 분리하면 원격 배포 의존성이 생긴다. 단순 중복 제거 목적으로 바꾸거나 전체 구조를 다시 작성할 필요는 없다.

## 남은 운영·공개 배포 작업

실제 NAS 단절·재연결·권한·여유 공간 및 대표 데이터의 처리량/RSS/DB/WAL 크기 검증이 남아 있다. 대상과 상태 디스크의 실행 중 여유 공간 감시도 개선 후보이다. 현재 소규모/loopback 결과를 100만~1000만 파일이나 실제 NAS 검증으로 해석하지 않는다.

공개 배포 전에는 사용자가 라이선스를 결정하고 Linux/Windows 및 원격 최소 버전 CI, wheel 설치 검증을 마련할 필요가 있다. 현재 저장소에는 LICENSE와 .github/workflows가 없다. include/exclude, 대역폭 제한, 작업 이력 조회 및 DB 백업/보존 정책은 추가 기능 후보이며 이번 검토에서 구현 범위로 확정하지 않았다.

## 검증 및 재현

격리된 Linux 임시 파일, 실제 rsync/loopback SSH 및 합성 SQLite로 세 재현 검사를 실행했다. 결과는 3 passed이며 발견 사항/측정 재현의 성공이다. 수정 완료나 전체 회귀 통과를 뜻하지 않는다.

SSH는 tests/test_ssh.py의 ssh_server/ssh_config fixture에서 Session.call을 원래 메서드에 위임하는 Counter 래퍼로 감싼 뒤 create_plan/execute를 각각 계수한다. 상태 조회는 state.database로 plans/entries를 생성하고 plan_lineage 삽입 전후 summary 시간을 perf_counter로 측정한다. 일회성 스크립트는 ignored work/review_20261022.py에 두었다. 기존 테스트와 운영 코드는 변경하지 않았다.

README, AGENTS, REQUIREMENTS, ARCHITECTURE, DEVELOPMENT의 지원 범위와 대조했다. 기능 계약은 유지하며 이번 미수정 발견 사항은 이 문서에 별도로 기록한다. 기존 성능 측정과 운영 수용 절차는 [PERFORMANCE.md](PERFORMANCE.md), [NAS_TESTING.md](NAS_TESTING.md), [DEVELOPMENT.md](DEVELOPMENT.md)를 참고한다.
